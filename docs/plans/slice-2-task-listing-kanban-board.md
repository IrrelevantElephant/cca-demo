# Slice 2 implementation plan: task listing and Kanban board

## Scope and completion gate

Implement a shared, read-only PostgreSQL-backed task board, task list/detail APIs, and manual refresh. Preserve the RecoverBoard shell, user selection, local-storage behavior, existing deployment gates, and single containerised Playwright runner. No task mutations, filtering, drag-and-drop, authentication, polling, infrastructure changes, or Slice 3 work.

This is an implementation plan and living progress report. Completion requires implementation plus successful relevant checks and real-stack Playwright verification; record unavailable checks and remaining gaps explicitly.

## Repository findings

Inspected root, Go, and frontend `AGENTS.md`; application Go/React/CSS; SQL and migration Dockerfile; app/test Compose; Playwright package/config/helpers/integration/smoke suites; both CI workflows; and `docs/TESTING.md` and `docs/TECHDEBT.md`.

- `src/main.go` uses method-aware standard-library routing, `database/sql`, and `lib/pq`. `/api/users` opens/closes a database handle per request using case-sensitive `ConnectionString`. Successful responses are JSON; errors use generic `http.Error` messages with server-side diagnostics.
- `src/database/schema.sql` is replayed by `src/Dockerfile.migrations`. There is no version ledger. The runner already provides a transaction, advisory lock, fail-fast behavior, and timeouts. `seed.sql` duplicates user seed definitions but is not run separately. Users 1/2/3 are explicitly guaranteed as Alice/Bob/Charlie by the existing SQL.
- `App.tsx` owns user fetching and selection and provides `UserContext`. The welcome placeholder contains `.current-user strong`, which integration and smoke tests assert. Retain this identity feedback outside the retired welcome card.
- React uses strict TypeScript, StrictMode, and plain CSS. There is no frontend unit-test script and no existing Go test suite.
- Playwright runs from one package/image/config, discovers specs in `integration/` and `smoke/`, and runs fully parallel. Core tests must continue using the real application/API/database.
- Test Compose removes host ports and supplies an isolated database volume. Production deployment currently updates the app before executing migrations; this documented rollout risk must not be hidden by mock or empty responses.

## 1. Add an additive, repeatable task migration

### Files and execution

1. Leave existing `schema.sql` and `seed.sql` unchanged; do not rewrite already-applied SQL.
2. Add `src/database/migrations/002_tasks.sql` containing task DDL and seed insertion.
3. Extend `src/Dockerfile.migrations` to copy the new file and execute it after `schema.sql`, using a second `--file` in the same existing `psql --single-transaction` invocation. Preserve advisory locking, error handling, and timeouts. Avoid introducing a migration framework or pretending a version ledger already exists.
4. Document the expanded entry point in `src/AGENTS.md` and the direct-psql workflow because running only `schema.sql` will no longer install the complete application schema.

### Schema decisions

- `id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`.
- `title TEXT NOT NULL` with a nonblank-title check.
- `description TEXT NULL`; API represents absent descriptions as `null`.
- `status TEXT NOT NULL CHECK (status IN ('todo', 'in_progress', 'done'))`.
- `priority TEXT NOT NULL CHECK (priority IN ('low', 'medium', 'high'))`.
- `assigned_to INTEGER NOT NULL REFERENCES users(id)` and `created_by INTEGER NOT NULL REFERENCES users(id)`. All tasks in this slice are assigned; unassigned-task semantics are deferred. Use default restrictive foreign-key deletion behavior, not cascading task deletion.
- `created_at` and `updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP`. Later mutation handlers will maintain `updated_at`; do not introduce mutation machinery now.
- Internal `seed_key TEXT UNIQUE`, nullable for future ordinary tasks. Exclude it from the public API.

### Stable seeding

Insert the ten suggested tasks with fixed, namespaced seed keys, covering every status/priority, all three assignees, multiple creators, and varied descriptions. Existing SQL guarantees user IDs 1–3, so referencing those IDs is valid and should be documented beside the seed definitions.

Use `ON CONFLICT (seed_key) DO NOTHING`. Never identify seeds by mutable titles or overwrite existing task values. Editing a seeded task later must leave its seed key untouched and must not cause duplicate insertion on migration replay. Missing seed keys are inserted; ordinary restarts do not change rows. Future deletion/tombstone policy is explicitly deferred, since a deliberately deleted seed could be recreated by replay.

### Database verification

On disposable databases only, test fresh installation, upgrade from the existing users-only schema, a second migration run, and preservation of unrelated rows. Modify a seeded task and replay: its ID, edits, and timestamps must remain unchanged. Verify all constraints reject invalid rows, seeds have valid user references, missing seeds are inserted, and container restart preserves task IDs/data. Keep these checks automated and run them in the existing Docker-based test workflow.

## 2. Implement read-only task APIs

### Structure

- Add `Task` to `src/types.go`, aligned with SQL and frontend types. Use `time.Time` timestamps and a nullable description representation that encodes as string or `null`.
- Add `src/tasks.go` for task query/repository functions and HTTP handlers; split further only if useful. Keep scanning/query logic separate from HTTP status and encoding logic.
- Register `GET /api/tasks` and `GET /api/tasks/{id}` in `src/main.go` using the existing mux and logging middleware.
- Follow existing connection setup rather than doing an unrelated global pooling refactor. Task operations share a small connection helper if needed, close resources, and derive a bounded query context (for example five seconds) from the request context.

### Contract

- List: explicit public columns, `ORDER BY created_at ASC, id ASC`, always a JSON array including `[]` for zero rows.
- Detail: parameterised `WHERE id = $1`; parse positive decimal integer IDs within PostgreSQL INTEGER bounds. Reject nonnumeric, signed, zero, negative, or overflowing IDs with 400; well-formed absent IDs return 404.
- JSON keys: `id`, `title`, `description`, `status`, `priority`, `assigned_to`, `created_by`, `created_at`, `updated_at`. Encode timestamps consistently as RFC 3339-compatible UTC strings.
- Query/scan/iteration errors produce generic 5xx responses and useful server-side diagnostics; never log credentials or substitute mock/empty task lists. Missing schema during rollout is an actual error with retryable frontend handling.
- No task write routes. Verify non-GET mutation requests are not accepted, without adding business functionality.

### Go tests

Add focused `httptest` tests with a small injectable task-reader boundary for handler success, empty list, malformed IDs, not found, cancellation/error mapping, and JSON shape. This is unit isolation only; Playwright contract tests must hit real PostgreSQL. Check the real SQL with disposable-database tests, including deterministic ordering and nullable description scanning.

## 3. Build the React board

### Components and state

- Extend `src/web/src/types.ts` with task/status/priority types, keeping existing user context intact.
- Add `src/web/src/TaskBoard.tsx` and small `TaskColumn`/`TaskCard` components, colocated initially unless size warrants separate files. Add a focused task payload validator/API helper rather than a new state-management dependency.
- Replace only the successful-user-load welcome placeholder in `App.tsx`. Preserve existing user loading/error/empty behavior, header/selector, local-storage key, and visible current-user feedback with the existing `.current-user strong` selector.
- Board receives the already loaded user list or consumes `UserContext`; build an ID/name map once. Never request users per task. Unknown IDs display `Unknown user`.
- Task fetching is independent of selected identity. Changing users does not filter, reorder, clear, or refetch the board.

### Loading and refresh behavior

- Track whether a valid response has ever loaded, current tasks, loading/refreshing status, retrieval errors, and validation warnings separately.
- Initial fetch: show a status indicator rather than a successful empty state.
- Refresh/Retry: fetch same-origin `/api/tasks` without navigation; disable duplicate refresh while pending, show refreshing status, and retain existing cards/counts.
- On success, atomically replace tasks/counts. On initial failure, show a visible alert and Retry. On refresh failure, retain the last good snapshot and label it as stale with an actionable alert. Never disturb user selection.
- Use `AbortController` and cleanup/request sequencing so unmounts, StrictMode effect replay, or stale responses cannot overwrite current state. No polling.

### Validation policy

Treat JSON as unknown. A non-array payload is a fetch/contract failure. Validate each record's identity, nonblank title, optional description, status/priority enums, user IDs, and timestamps; reject duplicate IDs predictably. Omit invalid records rather than guessing status/priority, retain valid ones, show a visible warning with the rejected count, and log concise diagnostic reasons/record IDs without dumping descriptions. If every record is invalid, show an invalid-data error, not `No tasks yet`; preserve a previous valid snapshot on an unusable refresh. Counts always reflect rendered valid records.

### Layout and accessibility

- On successful data load, render three labelled semantic column sections with headings and counts; preserve server order within each group.
- Cards show title, textual priority, and assignee; optional short description preview.
- Empty successful list shows `No tasks yet` while all three columns remain available, each with an empty-column message.
- Desktop CSS grid has three columns; narrow screens stack them. Reduce welcome-era padding, support long words/titles, and avoid horizontal overflow at 320px.
- Reuse branding, plain CSS, focus treatment, and contrast-aware priority styles. Use native buttons, semantic lists/cards, status/alert semantics, and accessible loading indication. No unnecessary framework or animation.

## Risks and explicit decisions

- **Migration history:** adding a numbered repeatable file does not establish historical migration tracking; broader versioning is deferred. Existing SQL remains untouched.
- **Rollout order:** additive DDL preserves the old app, but a newly deployed app may temporarily receive task-query failures before migrations finish. Show honest retryable errors and preserve user functionality. Report this existing limitation; changing deployment infrastructure/order is outside this slice.
- **Assignment/description nullability:** this plan chooses required assignee/creator IDs and nullable descriptions, consistently across SQL, Go, TypeScript, and contract tests.
- **Fixture complexity:** deterministic database-changing scenarios need their own app/database target to preserve parallel core-test isolation. Keep these services strictly test-only and use the same images/runner.
- **Persistence:** verify restarts against existing volumes; do not redesign development database storage or delete data as a shortcut.
