# Investigate possible cca-demo incidents

For log discovery/querying, follow `.agents/skills/search-logs-cca-demo/SKILL.md` exactly. That skill defines the Loki datasource, mandatory positive project selector, query restrictions, and reporting requirements. Do not duplicate or bypass its query guidance.

## Workflow

1. Clarify the symptom, affected service (if known), and incident time window. If unclear, use a bounded recent window (for example, the last 30 minutes) and say so.
2. Invoke the `search-logs-cca-demo` skill and query the scoped logs for evidence related to the symptom. Search for errors, elevated 5xx responses, timeouts, readiness failures, and unusually slow requests as appropriate. Preserve the required selector; use returned `resource_name` / `resource_instance` fields to identify the service and the `resource_id` label to identify its Scaleway container ID.
3. Separate observed facts from hypotheses. Report the queried time range, result count/truncation, key events with timestamps, affected resource, impact, and uncertainty. Empty results are not proof of health.
4. **Whenever the evidence identifies an incident, you MUST create a separate, purpose-built response script in the repository during this run. Do not stop at describing the recommended action, and do not defer script creation while asking the user to confirm the environment or authorize execution.** The script should contain the safest evidence-based steps to resolve the identified incident, interacting with infrastructure when that is appropriate. Read the repository-root `AGENTS.md` platform guidance and follow its Scaleway CLI target-selection and verification requirements. For Scaleway serverless-container incidents, use the Loki `resource_id` label as the container ID passed to `scw container container` commands; do not try to locate the affected container by matching `resource_name` as a container ID or rely on selecting the first name match. Use logged `resource_name`, `project_id`/project name, and region as corroborating evidence, then inspect the ID with the CLI. Before writing a mutating action, verify the returned container ID, name, project, and region against the incident and intended target. First inspect the actual CLI JSON shape; do not assume fields such as `project_name` exist or treat a missing/null field as a positive mismatch when it means the value is unavailable. Where the response omits project identity, use a read-only CLI lookup/configuration/context check to establish the project ID/name and compare it with the Loki `project_id`; if that cannot be independently verified, produce a read-only diagnostic script with operator-guided verification/remediation steps, not an automated mutation. Fail closed on genuine mismatches. A platform container status such as `ready` is not evidence that the application-level incident is recovered; use application health/readiness and fresh relevant logs or an endpoint check to verify recovery. Conversely, historical error logs establish the state during their timestamps, not necessarily the current state. If the logs contain multiple affected container IDs, validate and handle each explicitly rather than silently choosing one. Encode an interactive confirmation before any mutation; include post-action verification and explain impact, prerequisites, and rollback. Derive the target ID from evidence where possible, but require the operator to verify it before execution. Do not run the script, source it, or execute any commands from it that mutate infrastructure. Never perform production mutations during investigation, even if the script is ready. Never trigger the demo-only incident as part of investigation.
5. Create the response script using a unique timestamped filename generated in Bash:
   ```bash
   timestamp="$(date +%Y%m%d-%H%M%S)"
   script="scripts/${timestamp}-incident-response.sh"
   ```
   Write the script at `$script` (for example, `scripts/20261105-093752-incident-response.sh`). Do not overwrite an earlier script. Ensure the file is executable only if needed, and report its path and a brief description. The script must never execute automatically as part of investigation.
6. For the demo-only Break App incident, consult `src/AGENTS.md`: it is disabled unless `DEMO_INCIDENT_ENABLED=true`, must only be tested on a dedicated access-controlled instance, and recovery is by restarting the Go app process. When logs explicitly identify this incident and its recovery diagnostic, the response script should encode the documented app restart as an operator-confirmed action, with exact-target checks and verification. Do not trigger the incident during investigation or routine smoke tests; do not run the response script.
